# AI 知识库助手 PRD

## 1. 项目背景

企业内部资料通常分散在文档、网盘、项目空间、聊天记录和 Wiki 中。员工在查找制度、技术文档、业务流程或历史决策时，往往需要跨多个系统检索，效率低且容易遗漏上下文。

AI 知识库助手的目标是提供一个面向企业资料查询的 Web 应用：用户可以创建知识库、上传文档，并通过自然语言提问获得回答。系统在回答时应保留可追溯的来源，为后续 RAG 能力和企业级权限扩展打基础。

## 2. 目标用户

第一版只面向单个注册用户，不引入企业组织和多租户。

核心用户画像：

- 企业员工：希望快速查询公司制度、项目资料、产品文档、FAQ。
- 技术团队成员：希望把接口文档、部署说明、故障处理手册集中管理。
- 个人资料维护者或项目维护者：希望把分散资料整理成可问答知识库。

## 3. 解决的问题

第一版重点解决三个问题：

- 资料入口分散：用户可以把相关文档按知识库归档。
- 搜索成本高：用户可以用自然语言提问，而不是只依赖关键词搜索。
- AI 回答不可信：后续 RAG 阶段需要展示引用来源，让用户知道答案来自哪些文档内容。

## 4. 产品目标

MVP 的目标不是做完整企业知识管理平台，而是完成一个可部署、可演示、可扩展的 AI 应用闭环。

MVP 需要证明：

- 用户可以完成注册、登录和退出。
- 登录用户可以管理自己的知识库。
- 用户可以上传文档并查看文档列表。
- 用户可以发起 AI 对话并看到流式回答。
- 系统可以保存聊天历史。
- RAG 阶段可以基于文档内容回答并返回引用来源。

## 5. 使用场景

### 场景一：创建个人知识库

用户登录后进入控制台，创建一个名为“公司制度”的知识库，用于保存公司制度、报销规范、假期规则等资料。

### 场景二：上传资料

用户进入某个知识库后上传 PDF 或 TXT 文件。系统保存文件记录，并在后续阶段异步解析文本，为 RAG 检索做准备。

### 场景三：普通 AI 对话

在 RAG 未完成前，用户可以使用普通 AI Chat。前端提交问题，后端调用模型 API，并通过 SSE 将回答实时返回给前端。

### 场景四：基于知识库问答

RAG 完成后，用户可以选择某个知识库提问。系统检索相关文档片段，将片段作为上下文交给模型，并返回带引用来源的回答。

### 场景五：查看历史记录

用户可以查看之前的会话和消息，继续理解某个问题的上下文。

## 6. MVP 功能范围

### 用户模块

- 注册账号。
- 登录账号。
- 退出登录。
- 使用 JWT 保护需要登录的接口。

### 知识库模块

- 创建知识库。
- 查看当前用户的知识库列表。
- 查看单个知识库详情。
- 删除当前用户拥有的知识库。

### 文档模块

- 上传 PDF 或 TXT 文档。
- 查看某个知识库下的文档列表。
- 删除当前用户拥有的文档。
- 记录文档处理状态，为后续解析和 RAG 做准备。

### AI 聊天模块

- 发起新会话。
- 发送用户消息。
- 通过 SSE 接收流式回答。
- 保存用户消息和 AI 消息。
- 查看会话历史。

### RAG 模块

RAG 不作为第一周工程骨架的阻塞项，但属于项目核心里程碑。

RAG 阶段需要实现：

- 文档文本解析。
- 文本切片。
- Embedding 生成。
- 向量检索。
- 基于检索内容生成回答。
- 返回引用来源。

## 7. 非目标

第一版明确不做：

- 多租户组织空间。
- 企业成员邀请。
- 支付、订阅和套餐管理。
- 复杂 RBAC 权限模型。
- Agent 自动工作流。
- 文档协同编辑。
- 全文搜索高级语法。
- 企业级审计日志。

这些能力可以作为项目后续演进方向，但不进入 MVP。

## 8. 验收标准

Milestone 0 完成后，应能回答以下问题：

- 这个产品为谁服务？
- 第一版解决什么具体问题？
- 哪些功能属于 MVP，哪些不属于？
- 为什么先做普通 AI Chat，再做 RAG？
- 后续工程阶段需要哪些核心模块？

项目 MVP 完成后，应能演示以下流程：

1. 用户注册并登录。
2. 创建一个知识库。
3. 上传至少一个文档。
4. 发起一次 AI 对话并看到流式回答。
5. 查看保存的聊天历史。
6. RAG 阶段完成后，基于文档提问并看到引用来源。

## 9. 后续规划

MVP 之后按价值顺序扩展：

1. 文档解析队列：处理大文件和长 PDF，避免阻塞请求。
2. Redis 限流：保护登录和 AI 调用接口。
3. 对象存储：替换本地文件存储。
4. Docker 部署：提供本地和服务器一致的启动方式。
5. 基础权限增强：确保所有知识库、文档、会话都只能由所有者访问。
6. 企业化能力：在项目稳定后再考虑组织、多用户协作和权限角色。
